Why agents need protocols

You've built agents, given them tools and memory, and organised them into teams. The next step is communication: how agents connect reliably to outside tools, data and other agents, in a structured, reusable way.

As agents get more capable, this communication layer becomes critical. Without a standard, every new tool, service or partner agent means more custom integration code, more maintenance and more complexity. Two protocols tackle this from different directions:

MModel Context Protocol (MCP)

Standardises how agents and models connect to tools, resources and prompt templates, so an agent can discover and use outside capabilities without hard-coding every integration.

AAgent-to-Agent protocol (A2A)

Standardises how agents talk to other agents, so specialised agents can collaborate across teams and systems while keeping their internals private.

✦Think of it like this

MCP is the universal charging port: any device that has it works with any charger that has it, and nobody needs a drawer full of special cables. A2A is more like the way two companies email each other: each keeps its own staff and processes private, but they agree on how a request looks, how to reply, and how to follow up.

5.1

MCP: why tools need a standard

As agents grow, managing dozens or hundreds of tools gets hard. What if an agent could discover tools at run time, including tools built by other teams, without hard-coding each one? That's what the is for.

Agents need to reach APIs, databases and developer platforms. Without a standard, every model needs a custom integration for every tool, which quickly gets complex, costly and hard to maintain. A standard protocol gives one common interface for tool use: less integration work, better interoperability, and easier growth as new tools and models arrive.

What problem does MCP solve?

Imagine an enterprise agent that must work with your CRM, inventory database, email, calendar, document storage and more. Traditionally you'd write custom integration code for each system, keep it working as each system changes, handle authentication and authorisation for every one, juggle different API formats and conventions, and update the agent whenever a new system is added. That siloed approach leads to fragmented app development: every integration built from scratch, with no shared standard.

Worse, each AI app builds its entire stack on its own:

This doesn't scale. It's slow, error-prone, and couples your agent tightly to every system it touches. MCP replaces it with one standard layer that every AI app shares, a common protocol for tool calls and data access. The benefits:

Dynamic tool discovery

Your agent automatically sees every tool on the servers it's connected to.

No integration code

Connect to new tool sources without writing custom adapters.

Automatic updates

When a server adds or changes tools, your agent sees the change.

Unified interface

Tools from AWS, GitHub or your internal systems all work the same way.

Flexible deployment

MCP servers can run locally on your machine or remotely in the cloud.

5.2

How MCP works

MCP sets up a standard protocol between your agent and tool providers, much as USB set a universal standard for connecting devices to computers.

  1. 1

    Host

    The AI application or agent that needs to get things done: answer questions, retrieve information, use tools. It doesn't connect to outside systems directly; it talks to an MCP client.

  2. 2

    MCP client (tool consumer)

    Built into your agent. It connects to an MCP server, discovers the available tools and handles the protocol. When your agent needs a tool, the client calls the right server with the required parameters.

  3. 3

    MCP server (tool provider)

    A service that exposes a catalogue of tools with descriptions, parameters and capabilities. For example, AWS Labs publishes an MCP server for AWS documentation, GitHub publishes servers for repository operations, and you can build your own for internal systems.

  4. 4

    Data sources

    The real databases, APIs, files or enterprise systems behind the server. The server fetches what's needed and sends results back through the client to the host.

These parts work through one standardised communication layer, the core idea of MCP. Instead of every host and tool provider inventing its own integration, MCP defines one protocol for how clients and servers discover capabilities, exchange requests and return results. That shared protocol is what makes it scalable, reusable and easier to maintain.

The difference between a host and an MCP client

An MCP client never runs on its own. It's created and managed by a application, such as a code editor, an AI assistant or a browser extension. The host owns the user experience: the interface, session memory and prompt orchestration. It can run several clients at once, each connected to a different server.

Each , in contrast, is a protocol-level component with a one-to-one connection to a single . It discovers that server's tools, resources and prompts, gathers context for the model, and asks the user for missing information when needed. In short: the host is what users interact with; the client lets the host talk to one specific server.

iRemember it this way

The host is the application layer (UI, workflows, user interaction). The client is the integration layer inside the host that speaks MCP. The host orchestrates; each client talks to exactly one server.

Transports, lifecycle and authorisation

A client and its server exchange messages over a . MCP messages use and must be UTF-8 encoded. The client and server define what is said; the transport defines how it travels. There are two standard transports plus a custom option, all for the same job in different deployments:

Managing the lifecycle

management covers how a client and server start, maintain and end a connection: agreeing on protocol versions, learning each other's capabilities, and managing session state. Three stages:

  1. 1

    Initialisation

    Client and server agree on the protocol version and capabilities. Example: an agent connecting to a server for a company database performs the handshake, and the server confirms which features it offers, for example tools such as a run_query tool.

  2. 2

    Operation

    Normal protocol traffic. The agent asks for customer records; the server processes the requests and returns structured responses.

  3. 3

    Shutdown

    The client closes the connection gracefully, letting ongoing operations finish and releasing resources.

5.3

MCP server features

An MCP server offers clients three kinds of capability: tools to do things, resources to read things, and prompt templates to ask things the same way every time.

Tools

the agent can execute to act on outside systems: retrieving or searching data, sending messages, updating records.

Resources

Read-only, persistent data the server exposes: files, database records, API responses. They don't perform actions; they make information available to browse, search and reference, so a model can look up facts without triggering an operation.

Prompt templates

Predefined prompts the agent can use through the client to guide how it handles data or a task: document Q&A, transcript summarisation, structured JSON output.

A client typically uses them together: discover what the server offers, retrieve resources to gather context, invoke tools to act or fetch more data, and use prompt templates to structure the model's work.

Tools in MCP

You already know tools from Section 2. In MCP, tools are actions a server exposes, like built-in functions or APIs the LLM can call mid-conversation. When a request needs action (fetching data, triggering an operation, a calculation), the model picks the right tool. MCP expects a human in the loop: users should be able to see and approve tool calls, so they stay in control. Two protocol methods cover tools:

MethodWhat it does
tools/listDiscover the server's tools. Returns tool definitions with their input schemas.
tools/callRun one tool with arguments. Returns the tool's result.

Resources

A server can expose collections and documents as , which clients fetch, filter or search on demand. Clients send resources/list to discover them (and resources/templates/list for templates, covered below) and resources/read to get their contents.

Every resource has a unique (for example file:///path/to/document.md) and can declare a , a standard label that tells the client what kind of content it is (Markdown, JSON, PDF…) and how to handle it. For example, a server could share a course directory like this:

a resource description
{
  "uri": "file:///data/student-directory.json",
  "name": "courseDirectory",
  "title": "Course Directory",
  "description": "List of courses and instructors in a program",
  "mimeType": "application/json"
}

Resource templates

expose parameterised resources through URI templates. The client fills in the variables to ask for specific data. For example, travel://activities/{city}/{category} covers many cities and categories, and travel://activities/barcelona/museums asks for one. In this section's lab, greeting://{name} works the same way.

Scenario 1: directly querying a resource

A student assistant helps students find course and instructor information. A student asks: "Who is the instructor for the Machine Learning course?" The model realises it needs course information, the client fetches the right resource from the server, and the assistant answers from it:

Conceptually the request looks like findResource("courseDirectory", {"course": "Machine Learning"}). The resource holds structured information (course names, instructors, schedules, departments) that rarely changes, so reading it is enough.

Scenario 2: a resource and a tool together

Now the student asks: "Find the instructor for the Machine Learning course and send them a message asking about office hours." Reading isn't enough this time; something must happen.

  1. 1

    Query the resource

    courseDirectory identifies the instructor.

  2. 2

    Invoke a tool

    Something like sendMessage sends the instructor the question. Tools perform actions such as sending messages or scheduling meetings.

iRule of thumb

Resources provide information (course directories, schedules). Use them for static or semi-static data so the AI gets context quickly, without running unnecessary operations. Use tools when something must happen.

Prompt templates

MCP are predefined instruction templates a server exposes. They standardise recurring interactions and save you rewriting the same instructions. Each can have variables that the client fills in at run time; the client fetches the prompt from the server and passes the completed text to the model.

Prompts can be versioned and updated centrally without changing client code. They're explicitly chosen by the user or client; they never run on their own. And they can be context-aware, referring to available resources and tools to build richer workflows. Here's a template for a student study assistant:

a prompt template description
{
  "name": "generateStudyPlan",
  "title": "Generate Study Plan",
  "description": "Create a personalized study plan for a student based on their course and exam date",
  "arguments": [
    { "name": "course", "description": "Course the student is preparing for", "required": true },
    { "name": "examDate", "description": "Date of the upcoming exam", "required": true }
  ]
}

The client fills in the arguments, generateStudyPlan({"course": "Machine Learning", "examDate": "2026-05-10"}), and the template guides the model to a structured schedule leading up to the exam. In the lab, the same idea appears as generate_study_plan(course, exam_date).

5.4

MCP client features

Clients aren't just consumers. They can offer servers three things of their own: borrowed model access, safe folder boundaries, and a way to ask the user a question.

Remember that a client lives inside a host, such as a code editor or browser extension. That host has the AI model, the user's permissions and the user interface, so the client can offer:

Sampling

Let MCP servers use your AI model, safely.

Roots

Define the filesystem boundaries a server may work in.

Elicitation

Let a server request input from the user at run time.

Sampling

lets a server temporarily use the AI model and permissions the client already has, instead of calling a model of its own. It reverses the usual direction: rather than the client asking the server for data, the server asks the client to run an AI task for it. That's ideal when the server has the domain data or business logic, but the client has the model, the user's permissions and the UI. The user stays in control of model usage, approvals and final outputs.

A travel server retrieves many Rome activities but has no AI to rank them. It sends a sampling request asking the client's model to choose the top five for someone who loves history, art and food. The client asks the user for approval, runs the model, shows the results, and once the user approves, sends the final AI-generated list back to the server.

Roots

are the client's standard way to tell servers where in the filesystem they may operate: which directories and files they have access to. Servers can ask for the list of roots, and get notified when it changes.

Example: an event planner uses an MCP-powered assistant. The folder file:///Users/planner/conference-2025 is the workspace for the current event, so the client defines it as a root:

    5.5

    Using and building MCP servers

    Two ways to work with servers: use one that already exists, or build your own for your systems.

    Using pre-built servers

    Many ready-made servers exist, from Anthropic, the open-source community and AWS (through the official MCP servers for AWS from AWS Labs). You can connect, say, the GitHub MCP server or a Slack MCP server to an MCP host such as Claude Code, VS Code or Kiro, and every MCP-compatible agent can use their tools.

    A concrete example is the AWS Documentation MCP server, which exposes tools for searching and reading official AWS documentation. Your code launches it as a local process with uvx, creates an MCP client that talks to it over stdio, lists its tools, and hands them to a Strands agent. The agent then answers AWS questions from the docs rather than only from its training. You'll run exactly this in 5.7. You write no AWS-documentation integration code yourself: the server packages that capability as reusable tools.

    Building your own server

    To expose your organisation's tools and data, you build a custom server: use an SDK to define tools (actions) and resources (data), then run it with a chosen transport. Official MCP SDKs exist for many languages, including Python, TypeScript, Java, C# and Go; this course uses Python.

    FastMCP vs FastAPI
    What it isBuilt specifically for MCP, with MCP-native ways to define tools, resources and promptsA general-purpose web framework
    Choose it whenYou want an MCP server quickly, with little boilerplate, and the service mainly exposes MCP capabilitiesMCP is one part of a bigger service that also has REST APIs, custom auth flows, health checks or dashboards
    Trade-offFocused on MCPMore flexibility, but you write more of the MCP plumbing yourself
    ✦Think of it like this

    FastMCP is a ready-made food-truck kit: perfect when all you want to do is serve one menu, fast. FastAPI is a full restaurant kitchen: more to set up, but it can also run the bar, the bakery and the delivery counter.

    Using MCP from agent frameworks

    Frameworks such as Strands and LangChain act as MCP clients (or adapters): they let agents discover and call tools exposed by MCP servers. They don't define the server; they help agents consume MCP capabilities inside a bigger reasoning and orchestration flow.

    Strands

    Strands Agents ships with MCP support built on the official MCP Python SDK (which includes FastMCP). Use Strands for the agent, tool discovery and AWS connections, and FastMCP for the fast, focused tools the agent calls.

    LangChain

    The langchain-mcp-adapters library converts MCP tools into standard LangChain tools, so LangChain and LangGraph agents can use any MCP server.

    server.py, step by step

    server.py · imports and the server object
    """
MCP Server — exposes all the MCP primitives over stdio transport:

  * Tools      — get_weather, list_client_roots
  * Resources  — greeting://{name}  and  courses://directory (JSON)
  * Prompts    — weather_report, generate_study_plan

MCP (Model Context Protocol) lets LLM applications discover and call tools,
read resources, and use prompt templates through one standard protocol.

Run:  python client.py   (the client starts this server for you)
"""

import json

# FastMCP: high-level helper for building MCP servers. It handles JSON-RPC
# parsing, registration of tools/resources/prompts, and the transport.
from mcp.server.fastmcp import Context, FastMCP

# The name identifies this server to clients when they connect.
mcp = FastMCP("WeatherServer", log_level="WARNING")

    FastMCP is the high-level API from the official MCP Python SDK. It handles the protocol details for you: JSON-RPC messages, capability negotiation, and generating schemas from your type hints. The name "WeatherServer" is how the server introduces itself during the handshake; log_level="WARNING" keeps its own logs quiet.

    server.py · tool: get_weather
    # --- Tool: get_weather ---------------------------------------------------
# Tools are functions an LLM can call. @mcp.tool() registers the function so
# it appears in list_tools() and can be invoked with call_tool(). The
# docstring becomes the description the LLM sees.

@mcp.tool()
def get_weather(city: str) -> str:
    """Get the current weather for a given city."""
    # Fake data for demo purposes — a real server would call a weather API
    fake_weather = {
        "london": "15°C, cloudy",
        "paris": "18°C, sunny",
        "tokyo": "22°C, humid",
        "new york": "12°C, windy",
        "bangalore": "26°C, pleasant with light showers",
    }
    result = fake_weather.get(city.lower())
    if result:
        return f"Weather in {city}: {result}"
    return f"Sorry, no weather data available for '{city}'."

    @mcp.tool() registers the function so it appears in tools/list and can be run with tools/call. Just like Strands' @tool, the type hints become the input schema and the docstring becomes the description. The data is fake on purpose (including Bangalore, which the Strands lab asks about); a real server would call a weather API.

    server.py · tool that uses roots
    # --- Tool that uses a client capability: roots ---------------------------
# Roots are folders/URIs the *client* says the server may work within.
# A server can ask the client for its roots at any time.

@mcp.tool()
async def list_client_roots(ctx: Context) -> str:
    """List the workspace roots the connected client has shared with this server."""
    result = await ctx.session.list_roots()
    if not result.roots:
        return "The client did not share any roots."
    return "\n".join(f"{root.name}: {root.uri}" for root in result.roots)

    This tool shows the protocol running backwards. FastMCP injects a Context object (it is hidden from the input schema, which is why list_client_roots shows no arguments in tools/list); ctx.session.list_roots() sends a roots/list request from the server to the client and waits for the answer. Because it waits for a round trip to the client over the pipes, the function is async.

    server.py · resource template: greeting
    # --- Resource: greeting ---------------------------------------------------
# Resources are data an LLM application can read (like GET endpoints).
# "greeting://{name}" is a URI template: read_resource("greeting://Developer")
# fills in {name}. Use resources for data, tools for actions.

@mcp.resource("greeting://{name}")
def get_greeting(name: str) -> str:
    """Return a personalized greeting."""
    return f"Hello, {name}! Welcome to the WeatherServer."

    Resources are read-only data endpoints, like GET requests in a REST API. Because the URI contains {name}, this is a template: reading greeting://Developer calls the function with name="Developer".

    server.py · resource: course directory (JSON)
    # --- Resource: course directory (structured JSON) -------------------------
# A fixed URI with a MIME type tells the client how to interpret the content.

COURSES = [
    {"course": "Machine Learning", "instructor": "Dr. Rao", "weeks": 12},
    {"course": "Agentic AI on AWS", "instructor": "Shivank Agrawal", "weeks": 8},
    {"course": "Data Engineering", "instructor": "Ms. Iyer", "weeks": 10},

    "courses://directory",
    name="courseDirectory",
    title="Course Directory",
    description="List of courses and instructors in a program",

    return json.dumps(COURSES, indent=2)

    A fixed URI with a name, title, description and mime_type="application/json", the same shape as the resource description in 5.3, with a custom courses:// URI instead of a file path. The function returns the course list as JSON text.

    server.py · prompts
    # --- Prompts ---------------------------------------------------------------
# Prompts are reusable templates. Clients call get_prompt(name, arguments)
# and get back ready-to-send messages.

@mcp.prompt()
def weather_report(city: str) -> str:
    """Generate a prompt asking for a weather report."""
    return f"Please provide a detailed weather report for {city}, including temperature, humidity, and forecast."


@mcp.prompt(title="Generate Study Plan")
def generate_study_plan(course: str, exam_date: str) -> str:
    """Create a personalized study plan for a student based on their course and exam date."""
    return (
        f"Create a week-by-week study plan for the course '{course}'. "
        f"The exam is on {exam_date}. Include revision weeks, practice tests, "
        "and one concrete goal per week."
    )

    @mcp.prompt() registers reusable templates. A client calls get_prompt("weather_report", {"city": "Tokyo"}) and gets back ready-to-send messages. generate_study_plan is the lab's version of the study-plan template from 5.3, with a title.

    5.8

    A2A: agents talking to agents

    MCP connects an agent to tools. But what about connecting an agent to another agent, perhaps built by a different team, in a different framework, running somewhere else?

    The is a standard bridge that lets agents built on different stacks (LangGraph, CrewAI, Google ADK, Strands and others) communicate, discover each other and manage shared workflows, even across organisations. Google introduced it in 2025; it has since merged with IBM's Agent Communication Protocol (ACP) and is now a vendor-neutral project governed by the Linux Foundation.

    A2A is about peer-to-peer collaboration between agents: they can delegate complex tasks and solve open-ended problems while keeping their internals private. MCP, in contrast, connects agents to specific tools and functions.

    MCP vs A2A: why not just wrap an agent as a tool?

    MCP reduces the complexity of connecting agents to tools and data. Tools are usually and do one predefined thing (a calculator, a database query). So could you simply expose an agent as an MCP tool? Sometimes, and Section 4 did something similar inside one program. But as a general approach for independent agents it's limiting: tools execute actions; agents solve problems. Squeezing an agent into a tool call hides what it can really do: handle ambiguity, ask follow-up questions, run multi-step and long-running work, report progress.

    A2A complements MCP. It lets agents collaborate in their natural mode, talking as agents (or as users) rather than as function calls, which enables multi-turn interactions where agents reason, plan and delegate.

    1. 1

      The patient's request goes to the diagnosis agent

    2. 2

      It talks to the insurance agent over A2A

    3. 3

      Each agent acts with its own MCP-connected tools

      The diagnosis agent reaches the hospital's systems; the insurance agent reaches insurance and pharmacy APIs.

    4. 4

      Information flows back and forth over A2A until the task is complete

    Why agents need a standard protocol

    As agents become more capable they also become more specialised, and more likely to work inside a larger multi-agent system. But the ecosystem is fragmented across frameworks, vendors and styles. A2A gives them a common protocol to communicate and coordinate across organisational and technical boundaries, without sharing their internals.

    ReasonIn detail
    Solve framework fragmentationAgent frameworks (LangGraph, CrewAI, Microsoft's framework and others) aren't compatible out of the box. A2A lets agents talk whatever model or language they use.
    Enable complex collaborationTasks like planning a whole trip (flights, hotels, activities) need several specialised agents; A2A gives the structure and methods to coordinate them.
    A common language (the HTTP analogy)The web needed HTTP to move data between different systems; the agent world needs A2A as a universal bridge beyond siloed apps.
    Cross-organisation workflowsAgents collaborate across teams and companies while staying opaque: no internal implementation or private code is exposed.
    Preserve agent capabilitiesAgents handle ambiguity, multi-step workflows, coordination and open-ended goals. Reducing them to one tool call loses that; A2A supports the richer interaction.
    Vendor neutralityHosted by the Linux Foundation and governed by a technical steering committee, so no single company controls how agents interact.

    A2A by example: a product launch

    A marketing manager asks an AI system: "Create and execute a launch plan for our new eco-friendly smartphone in the European market." That needs many specialities, so (just like the multi-agent patterns in Section 4) a lead orchestrator agent breaks it down and works with:

    Each specialist sits on its own system: market research on proprietary data, supply chain on the company's , creative content on an AI creative tool, legal on a secure legal model. Without A2A, each agent has its own bespoke development and deployment, so they can't collaborate, let alone discover what each other can do. A2A acts as the common communication layer: the orchestrator can discover agents by capability, agents exchange information in a shared format, and one agent can even verify or approve another's output. The orchestrator then combines everything into one launch playbook, turning weeks of human coordination into a fast, automated workflow.

    iSwarm vs A2A

    The swarm pattern from Section 4 organises agents inside one multi-agent system. A2A solves a different problem: standard communication between independently built agents, across frameworks, platforms and organisations. You could even run a swarm whose members talk A2A.

    5.9

    How A2A works

    The protocol standardises only the bridge between agents. Agent A doesn't need Agent B's code, prompts or database; it only needs to format an A2A request and read an A2A response.

    Agent A: the client agent

    Starts the conversation and asks for work. Usually the front-facing agent that talks to the end user. It discovers other agents by reading their to see what they can do.

    Agent B: the remote (server) agent

    Receives the request and does the work. It hosts its capabilities at a URL and publishes its agent card at /.well-known/agent-card.json. It decides how to fulfil a request: a simple one gets a message straight back; a complex one becomes a task it manages until it produces an artifact (the result).

    iOpaque by design

    A remote agent never has to show how it works inside: which code, which model. It only has to produce the output the protocol defines.

    Discovery and protocol bindings

    Agents find each other through agent cards: JSON files at a well-known URL, a bit like an , acting as a digital business card. A card details the agent's name, capabilities, supported protocols, media types and authentication requirements, including its URI (endpoint) and its supported .

    A binding tells the client agent exactly which technical format to use with that remote agent. A2A provides the language; the binding is the physical connection that carries it.

    ✦Think of it like this

    You've written a letter in English (the common language, A2A). How do you send it? HTTP binding is ordinary post: the most common and easiest. gRPC binding is a high-speed courier: faster and more efficient for heavy data. JSON-RPC binding is a telegram: it follows a strict set of remote-control rules.

    BindingIn practice
    JSON-RPCJSON-RPC 2.0 over HTTP, with server-sent events for streaming. The binding this section's lab uses.
    gRPCBinary, high-performance remote calls (); good for heavy traffic
    HTTP + JSON (REST)Plain HTTP endpoints with JSON bodies

    If one agent only speaks gRPC and the other only HTTP+JSON (REST), they can't talk directly. They must agree on a binding, which is exactly what their agent cards declare.

    The A2A data model: messages, tasks, artifacts

    1. 1

      Message

      The client sends a (one turn of interaction) made of one or more parts: text, JSON data, files.

    2. 2

      Task

      When the remote agent starts working, it may create a to track progress over time, with an ID and a status.

    3. 3

      Artifacts

      As the task progresses or completes it produces , output containers that also hold parts.

    4. 4

      GetTask

      The client can call GetTask at any time to retrieve the latest status and whatever artifacts exist so far.

    Communication styles

    Tasks differ: some finish in a second, some take hours. A2A supports four ways of exchanging them:

    Synchronous

    For simple, immediate answers. Agent A sends a message with SendMessage; Agent B processes it and replies right away. The client waits for the result, so it suits quick, short-lived tasks.

    Asynchronous (polling)

    For complex or long-running jobs where the client shouldn't block. Agent B replies with a task object instead of the final result: a task ID plus a status. Agent A carries on and periodically calls GetTask with that ID. When the task reaches a completed state, the results come back as artifacts.

    In the Python A2A SDK, a plain message/send waits for the answer by default. To poll instead, the client sets ClientConfig(polling=True); the request then asks the server not to block, and the client calls GetTask (tasks/get) in a loop until the task is finished.

    Streaming

    Uses server-sent events to deliver real-time updates or text in chunks as it's generated, so you see live progress. It's only available if the server sets capabilities.streaming = true in its agent card. Agent A calls SendStreamingMessage; the server keeps an HTTP connection open (text/event-stream) and sends structured events (status changes, intermediate messages, partial results) until the task completes.

    Push notifications

    For tasks that take a long time, or when the client can't stay connected. Instead of polling or streaming, the client gives a URL and the server calls it when something important happens, such as completion or "input required". A pharmacy agent might notify a healthcare system hours later when a prescription is ready; a flights agent might notify when a booking is confirmed. Ideal for long-running, event-driven work.

    Push notifications only work if the server declares capabilities.pushNotifications = true in its agent card. Agent A supplies a PushNotificationConfig (webhook URL plus optional authentication) with the first request or through a separate call. Agent B then POSTs to that webhook on significant updates, and Agent A usually follows up with GetTask to fetch the full task and results.

    ?Method names on the wire

    The A2A spec names its operations SendMessage, SendStreamingMessage and GetTask. With the JSON-RPC binding and the a2a-sdk 0.3 used in this section, they travel as the methods message/send, message/stream and tasks/get.

@tool
def search_flights(origin: str, destination: str) -> str:
    """Search for available flights between two cities.

    Args:
        origin: Departure city name.
        destination: Arrival city name.

    Returns:
        A formatted list of available flights or a message if none found.
    """
    # Normalize both cities to lowercase for dictionary lookup
    key = (origin.strip().lower(), destination.strip().lower())
    flights = FAKE_FLIGHTS.get(key)

    # If no flights found, show the user what routes are available
    if not flights:
        available = [f"{o.title()} -> {d.title()}" for o, d in FAKE_FLIGHTS.keys()]
        return (
            f"No flights found from {origin} to {destination}. "
            f"Available routes: {', '.join(available)}"
        )

    # Format each flight as a readable line
    lines = [f"Flights from {origin.title()} to {destination.title()}:"]
    for f in flights:
        lines.append(
            f"  {f['airline']} {f['flight']}: depart {f['depart']}, "
            f"arrive {f['arrive']}, price {f['price']}"
        )
    return "\n".join(lines)


@tool
def book_flight(flight_number: str, passenger_name: str) -> str:
    """Book a specific flight for a passenger.

    Args:
        flight_number: The flight number to book (e.g. AE101).
        passenger_name: Name of the passenger.

    Returns:
        Booking confirmation or error message.
    """
    # Search all routes for the matching flight number
    for flights in FAKE_FLIGHTS.values():
        for f in flights:
            if f["flight"].upper() == flight_number.strip().upper():
                # Generate a fake confirmation number from a hash
                return (
                    f"Booking confirmed! {passenger_name} is booked on "
                    f"{f['airline']} flight {f['flight']} "
                    f"(depart {f['depart']}, arrive {f['arrive']}). "
                    f"Total: {f['price']}. Confirmation #: TRV-{hash(flight_number + passenger_name) % 100000:05d}"
                )
    return f"Flight {flight_number} not found. Please search for available flights first."

      # --- Helper: Build an A2A Message ----------------------------------------
# Creates a standard A2A Message object that the server expects.
# This is the equivalent of a user typing a question in a chat.

def make_message(text: str) -> Message:
    return Message(
        kind="message",          # Always "message" for chat messages
        role=Role.user,          # We're the user sending a question
        parts=[Part(TextPart(    # Wrap the text in a TextPart inside a Part
            kind="text",
            text=text,
        ))],
        message_id=uuid4().hex,  # Unique ID for this message
    )


# --- Helper: Extract Text from A2A Response ------------------------------
# A2A servers return a "task" object. The actual answer text lives inside
# task.artifacts[].parts[].text. This function digs it out.

def extract_text(result) -> str:
    """Pull text out of an A2A task response (from artifacts)."""
    if hasattr(result, "artifacts") and result.artifacts:
        texts = []
        for artifact in result.artifacts:
            for part in artifact.parts:
                # The a2a SDK wraps parts in a discriminated union (Part.root)
                if hasattr(part, "root") and hasattr(part.root, "text"):
                    texts.append(part.root.text)
                elif hasattr(part, "text"):
                    texts.append(part.text)
        if texts:
            return "".join(texts)
    # Fallback: return the raw string representation
    return str(result)

        make_message: build an A2A message

        A Message with role=Role.user, one text part (Part(TextPart(...))), and a unique message_id. It's the A2A equivalent of a user typing in a chat box.

      2. 3

        extract_text: dig the answer out

        A2A servers return a task; the answer lives in task.artifacts[].parts[]. The SDK wraps each part in a container that can hold any kind of part (text, file or data) and keeps the real part in part.root, so the code checks both shapes and falls back to the raw text if needed.

      # --- Core: Send a Message to an A2A Agent --------------------------------
# This is the main A2A client logic. It:
#   1. Fetches the agent card to discover capabilities
#   2. Auto-selects streaming or sync mode based on the card
#   3. Sends the message using the A2A protocol
#   4. Extracts and returns the text response

async def send_a2a_message(base_url: str, text: str) -> str:
    """Send a message to an A2A agent, auto-selecting streaming or sync based on the agent card."""
    async with httpx.AsyncClient(timeout=TIMEOUT) as hc:

        # Step 1: Fetch the agent card from /.well-known/agent-card.json
        # This tells us the agent's name, skills, and whether it supports streaming
        resolver = A2ACardResolver(httpx_client=hc, base_url=base_url)
        card = await resolver.get_agent_card()

        # Step 2: Check the agent card capabilities to decide the mode
        # If the server advertises {"capabilities": {"streaming": true}},
        # we use SSE streaming; otherwise we use sync (single response)
        use_streaming = bool(card.capabilities and card.capabilities.streaming)
        mode = "streaming" if use_streaming else "sync"
        logger.info(f"Connected to: {card.name} — mode: {mode}")

        # Step 3: Create an A2A client configured for this agent
        # ClientConfig sets streaming mode; ClientFactory builds the client from the card
        config = ClientConfig(httpx_client=hc, streaming=use_streaming)
        client = ClientFactory(config).create(card)

        # Step 4: Send the message and process response events
        # In sync mode: yields one task with artifacts (the final answer)
        # In streaming mode: yields intermediate Messages + final task with artifacts
        msg = make_message(text)
        final_text = ""

        async for event in client.send_message(msg):
            # Task with artifacts — this is the final complete response
            if hasattr(event, "artifacts") and event.artifacts:
                final_text = extract_text(event)

            # (Task, UpdateEvent) tuple — check for artifacts on the task
            elif isinstance(event, tuple) and len(event) == 2:
                task, _ = event
                if hasattr(task, "artifacts") and task.artifacts:
                    final_text = extract_text(task)

            # Intermediate streaming Message — we skip these and wait for
            # the final artifacts which contain the complete answer
            elif isinstance(event, Message):
                pass

        return final_text if final_text else "No response received."

        Fetch the agent card

        A2ACardResolver(...).get_agent_card() downloads /.well-known/agent-card.json: name, skills, capabilities.

      2. b

        Pick the mode from the card

        If the card says streaming: true, use streaming (SSE); otherwise a single synchronous response. That's capability negotiation in two lines.

      3. c

        Create a client for that agent

        ClientFactory(ClientConfig(...)).create(card) builds a client configured from the card: URL, binding, streaming.

      4. d

        Send and read the events

        client.send_message(msg) sends the JSON-RPC request and yields events. Both cards in this lab say streaming: true, so it is always message/stream here; against an agent without streaming, the same code would send message/send. A task with artifacts, or a (task, update) pair, carries the answer; intermediate streaming messages are skipped until the final artifacts arrive.

      Both protocols together: A2A outside, MCP inside

      In this lab the weather agent keeps its data in a Python dictionary. In a real system it would more likely get weather from an MCP server, which is exactly what you built in Lab 5.6. The two protocols then sit at different layers: A2A between agents, MCP between each agent and its tools. The orchestrator doesn't notice the change at all, because the weather agent is opaque.

      To try it, change only the agent in weather_agent_server.py, reusing the MCPClient pattern from Lab 5.7. Recent Strands versions accept an MCPClient directly in tools=[...] and open and close the connection for you:

      weather_agent_server.py · optional change
      import sys
from pathlib import Path
from mcp import StdioServerParameters, stdio_client
from strands.tools.mcp import MCPClient

# The MCP server from Lab 5.6, started as a child process over stdio
SERVER = Path(__file__).resolve().parent.parent / "mcp-basics" / "server.py"
mcp_client = MCPClient(
    lambda: stdio_client(StdioServerParameters(command=sys.executable, args=[str(SERVER)]))
)

weather_agent = Agent(
    model=BedrockModel(model_id=MODEL_ID, region_name=REGION),
    name="Weather Agent",
    description="Provides current weather information for cities around the world.",
    system_prompt="You are a helpful weather assistant. Be concise and friendly.",
    tools=[mcp_client],      # tools now arrive over MCP instead of @tool
    callback_handler=None,
)

      Recap and self-check

      Your agents can now plug into any tool that speaks MCP, and talk to any agent that speaks A2A.

      Standard protocols make agentic systems easier to build, extend and scale. You started with MCP, which solves the explosion of custom integrations between many AI apps and many tools: instead of N × M connectors, everything speaks one shared interface through hosts, clients and servers. You saw how messages travel (JSON-RPC over stdio or Streamable HTTP), how a connection is set up and closed (the lifecycle), how remote servers are protected (authorization), and what servers offer: tools to act, resources to read and prompt templates to ask consistently. Clients can offer things back: sampling, roots and elicitation.

      Then you met A2A, which solves a different problem: letting agents, open-ended problem solvers rather than simple tools, collaborate without exposing their insides. Agents discover each other through agent cards, exchange messages, track work as tasks and return artifacts, in four interaction styles: synchronous, asynchronous polling, streaming and push notifications.

      In the labs you built an MCP weather server with FastMCP, called it from a raw client and from Strands agents, and then ran a travel orchestrator that talks to weather and flights agents over A2A. The two protocols complement each other: A2A for collaboration between agents, MCP for each agent's own work with tools and data.
